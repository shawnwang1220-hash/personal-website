## 一、问题：如何将网站访问行为与后续线索关联？

GA4 可以记录用户的页面浏览、表单提交等行为，但这些行为数据与实际提交的线索信息通常分开存储。如果希望后续分析某条线索在提交表单之前的网站行为，就需要找到一个在两套数据里都存在的标识符。

GA4 Client ID 是识别同一浏览器访问者的标识。将它采集到线索记录中，可以为后续的行为关联分析提供基础。本项目需要解决三个问题：

- 如何在用户提交表单时获取 GA4 Client ID？
- 如何将这个标识符随表单一起提交，并保存在线索记录中？
- 如何验证线索记录中的 Client ID 与发送给 GA4 的 Client ID 一致？

## 二、做法：建立采集、传递、存储和验证链路

### 1. 从浏览器 Cookie 中获取 Client ID

通过 JavaScript 读取浏览器中的 `_ga` Cookie，解析出 GA4 Client ID，写入表单隐藏字段。用户正常填写和提交表单时无需额外操作。

`_ga` 的值形如 `GA1.1.<前段>.<后段>`，取后两段拼接即为 Client ID。

该字段为非必填，以下三种情况会使它为空：

| 情况 | 原因 |
| --- | --- |
| 广告拦截或隐私扩展 | `googletagmanager.com` 被拦，GA4 未初始化，Cookie 不存在 |
| 未启用 JavaScript 的提交 | 原生表单提交，脚本未执行，隐藏字段为空字符串 |
| Safari 的 ITP | 第一方 Cookie 有 7 天上限，过期后重新生成 |

第三种需要单独说明：Cookie 仍然存在，但已经是新的 Client ID。同一访客隔周再访问时标识会变化，基于该标识的回溯会在中间断开。

**格式变化与选型说明**

Cookie 中的会话标识存在两种格式：`GS1.1.<会话号>…` 与 `GS2.1.s<会话号>$…`，后者多一个 `s` 前缀。按前一种格式编写的解析逻辑在后者下会返回空值，且不产生任何错误提示。

这类问题现在有更稳妥的方案。GTM 于 2025 年 12 月提供了内置的 Client ID、Session ID、Session Number 变量，直接读取 GA4 内部状态而非解析 Cookie，因此不受格式变化影响。

本项目的容器未启用这些内置变量；且内置变量需要额外配置标签才能写入表单字段，存在标签执行晚于用户提交的可能。因此仍采用直读 Cookie 的方式。这是选型上的取舍，不是实现难度的差异。

### 2. 将 Client ID 保存到线索记录

表单提交后，数据发送至后端处理并保存，Client ID 作为线索数据的一部分与其他字段一同写入。查看实际生成的记录，可以确认该值已经从前端传递到数据存储环节，而不只停留在页面中。

隐藏字段对用户可见、可修改，因此后端需要对格式进行校验：符合 Client ID 形态的值予以保留，其余按空值处理。这一校验的前提是，该字段用于补充分析，其异常不应影响线索的正常接收。因此写入在前，下游步骤各自容错，不回滚主记录，也不向访客暴露错误。

### 3. 将 Client ID 作为事件参数上报至 GA4

在表单提交成功时向 dataLayer 推送事件，并将 Client ID 与 Session ID 作为事件参数一同传递，由 GTM 读取后上报至 GA4。

未在 GA4 中注册自定义维度，原因与基数有关。Client ID 一人一值，基数等于访客数。GA4 报表的行数存在上限，超出部分不会被丢弃，而是合并进一行 "(other)"，只保留最常见的取值。Google 对高基数的判定参考是单个维度的值超过 500 个。将其注册为自定义维度的实际结果是：大部分记录落在 "(other)" 中，无法用于逐条分析，同时占用一个维度名额。

需要查看明细时，通过 BigQuery 导出数据，其中 `user_pseudo_id` 即 Client ID。

### 4. 验证两条链路的数据一致性

完成配置后分别检查两处数据：

- 线索记录中可看到表单提交时保存的 Client ID；
- GA4 DebugView 中表单提交事件正常触发，并包含预期的参数值。

本项目两条链路共用同一份 Cookie 解析结果，一致性由取值来源保证。验证的目的是确认该值在经过表单提交、后端处理与数据存储后仍然完整，未在传输环节丢失或截断。

如果后续改用 GTM 内置变量获取事件侧的取值，两条链路的来源将不再相同。此时交叉验证才具备独立价值，可以暴露 Cookie 被改写或解析错误这类单一路径无法发现的问题。

## 三、结果：完成从浏览器标识符到线索记录的闭环

采集、传递、存储与上报四个环节均已验证：从 `_ga` Cookie 解析出 Client ID，经表单隐藏字段提交至后端并保存，在线索记录中可查看，同时作为事件参数出现在 GA4 DebugView 中。

本项目完成的是数据采集与链路验证。尚未实施基于 BigQuery 的行为与线索关联分析，也未评估该方案对线索转化率或获客成本的影响。

## 四、学到：数据采集成功，不等于业务分析已经完成

### 1. 标识符必须贯穿数据链路

前端能够读取一个标识符，并不意味着它最终会出现在业务数据中。只有确认它经过表单提交、后端处理和数据存储后仍然可用，才能说明链路已经打通。

### 2. 同一个标识符可以服务于不同的数据链路

线索采集与事件上报服务于不同目的，可以共用同一个取值。共用来源时，一致性由构造保证；来源不同时，交叉验证才具有独立意义。区分这两种情况，决定了验证工作本身有多大价值。

### 3. 采集可行与可用于分析是两个问题

将 Client ID 作为事件参数上报，并不意味着它能在 GA4 标准报表中作为维度使用。高基数维度会因行数上限被合并为 "(other)"。需要明细级关联时，应通过 BigQuery 导出后处理。这属于后续扩展方向，不在本次交付范围内。
