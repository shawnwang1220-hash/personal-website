我的公众号只有一篇文章，很久没登录了。想看看有没有办法让写文章这件事省点力。

真正卡住我的不是技术，是三份互相打架的材料。

| 信息源 | 它说 |
|---|---|
| 官方文档 `draft/add` | 适用范围表：公众号 ✔ 服务号 ✔，**没有"仅认证"标注** |
| 社区实测帖 | 未认证个人订阅号调这个接口，直接 48001，没权限 |
| 各类教程与工具文档 | "必须已认证公众号（个人 / 企业）" |

三份材料，两个相反结论。争是争不出来的，只能拿自己的账号实调一次，看返回码。

先说结论，再讲过程。

- **草稿链路能用**：换 access_token、上传永久素材、创建草稿，三个接口实测全通。
- **发布链路必死**：`freepublish/submit` 官方明文标注"仅认证"，个人主体拿不到。
- **实际收益**：排版、配图、封面、进草稿箱全自动，最后点一下发布还得自己来。
- **过程中踩了五个坑**，其中三个属于"文档没错、照着做会翻车"，还有一个是**文档直接写错了**。

如果你也是个人订阅号，只想省掉排版那一小时，这条路是通的。

## 一、选型：三条路，先算清代价

在动手之前，路线有三条。

| 路线 | 门槛 | 能做到哪一步 | 代价 |
|---|---|---|---|
| API 直连 | 企业主体已认证（仅发布环节） | 草稿 → 发布全自动 | 官方接口，合规，长期可维护 |
| 浏览器会话自动化 | 无 | 只能存草稿 | 复用登录态直调后台接口，违反平台协议，有封号风险 |
| 人工粘贴 | 无 | AI 排版好 HTML，人来粘贴 | 没风险，但最后一步必须手动 |

第三条是保底方案，随时能退回去。第二条直接排除——为了省十分钟去赌一个号，不划算。

真正要验证的只有第一条。

## 二、反常识结论：卡住你的是「认证」，不是「实名」

社区里"个人号一律没权限"的说法流传很广。这句话的来源我后来查到了：**2025 年 7 月，微信回收了个人主体账号的 `freepublish` 发布接口权限。**

这条政策被大量教程简化成了"个人号没有接口权限"。

被回收的只是发布链路。草稿链路从来没被收走。

官方依据藏在迁移说明文档的一段附注里，几乎没人引用。原文把两条门槛**分列**开了：

| 账号类型 | 未完成时提示 | 解决方式 |
|---|---|---|
| 个人主体 | 该账号尚未完成**实名**，前往微信公众平台完成实名后重试 | 管理员实名（在「设置与开发 - 人员设置 - 管理员信息」完成） |
| 非个人主体 | 该账号尚未完成**主体认证**，前往微信公众平台完成认证后重试 | 申请微信认证 |

**这是整件事的关键：卡你的是「认证」，不是「实名」。**

个人订阅号做不了企业主体微信认证，所以发布接口永久关闭；但管理员实名是能做到的，所以草稿链路能开。

官方文档的适用范围表也印证了这一点：

| 接口 | 公众号 | 服务号 |
|---|---|---|
| `draft/add` 新增草稿 | ✔ | ✔ |
| `material/add_material` 上传永久素材 | ✔ | ✔ |
| `media/uploadimg` 上传正文图 | ✔ | ✔ |
| `freepublish/submit` 发布草稿 | **仅认证** ✔ | ✔ |

前三个接口没有任何"仅认证"标注。第四个有。

所以这次实测的目标很明确：不奢求发布，只确认草稿箱能不能写进去。

## 三、配置：入口搬过家了，AI 在这里翻第一次车

要调接口，得先有 AppID 和 AppSecret，还得把调用方的 IP 加进白名单。

我的 AI 助手先是很有把握地告诉我："IP 白名单只在公众平台后台配，不用去开发者平台。"

这个判断是错的。

**2025 年 12 月 1 日起，微信把整个「开发接口管理」从公众平台后台整体迁移到了「微信开发者平台」。** 老的【设置与开发 → 开发接口管理】路径已经失效，而网上大量教程还是旧的，照着做会找不到入口。

现在有三个站特别容易搞混：

| 站点 | 域名 | 干什么的 |
|---|---|---|
| 微信公众平台 | mp.weixin.qq.com | 写文章、看数据、账号设置 |
| 微信开发者平台 | developers.weixin.qq.com/platform/ | AppID、AppSecret、IP 白名单都在这 |
| 微信开放平台 | open.weixin.qq.com | 做 App / 网站微信登录用，跟公众号接口无关 |

正确路径是：**微信开发者平台 →「我的业务」→ 选中你的公众号 →「基础信息 → 开发密钥」**。AppID、AppSecret、API IP 白名单三个东西都在这一页。

### IP 白名单的三个细节

1. **顺序有陷阱**：如果页面上找不到白名单的编辑入口，是因为 AppSecret 还没启用。必须先启用或重置 AppSecret，白名单的按钮才会出现。
2. **格式有限制**：只能填单个公网 IP，不支持网段（`1.2.3.4/24` 这种会失败）。填多个用换行分隔，不是逗号也不是分号。
3. **不会立刻生效**：保存需要管理员扫码，之后还要等 5 到 10 分钟。刚存完立刻测，一定失败——这一点最容易让人误以为配错了。

另外每次修改白名单都要管理员扫码，全程手机得在手边。AppSecret 更是只显示一次，重置旧的就立刻失效，务必当场存好。

## 四、实调：六次调用，三次失败

配置完成后，按顺序调接口。过程不算顺利。

| 次序 | 调用 | 结果 |
|---|---|---|
| 1 | 换 access_token | ❌ 40164 IP 不在白名单 |
| 2 | 换 access_token | ✅ 成功（白名单生效后） |
| 3 | 上传封面素材 | ✅ 成功，拿到 media_id |
| 4 | 创建草稿 | ❌ 40007 invalid media_id |
| 5 | 创建草稿（修参数） | ❌ 40007 还是它 |
| 6 | 创建草稿（再修） | ✅ 成功 |

### 第一次失败：40164，白名单

报错的原文很有意思：

```
invalid ip 114.240.xxx.xxx ipv6 ::ffff:114.240.xxx.xxx, not in whitelist
```

它同时回显了两个 IP：一个纯 IPv4，一个带 `::ffff:` 前缀的映射形式。这是微信服务端双栈造成的。通常填 IPv4 就行，但如果填了还报错，就得补上那个映射形式——确实存在只认后者的账号。

**有个附带收获：报错里回显的 IP，是微信服务器实际看到的来源 IP。它比你本机自己探测的结果更可信，直接拿它去填白名单最稳。**

### 第二次失败：40007，封面是硬性要求

白名单通了之后，access_token 顺利拿到。我以为接下来是顺水推舟，结果卡在了草稿接口。

第一次报 40007 invalid media_id。我当时传了空的 `thumb_media_id`。

第一次修正：把整个字段删掉，不传。

第二次报错：还是 40007。

这才明白：**封面不是可选项，是硬性要求。** 空字符串不行，字段缺失也不行。

于是补了一步：本地用代码生成一张 900×383 的测试图（微信推荐的封面比例），上传到永久素材库拿到 media_id，再把它作为封面去建草稿。

第三次，成功了。

## 五、五个坑，都是实测踩出来的

前四个坑的共同点是：**文档没有明说，或者说了但容易理解偏。** 第五个不一样——**文档直接写错了**。

### 坑一：微信接口成功时不返回 errcode

这是个要命的细节。比如上传素材成功，微信返回的是：

```json
{"media_id":"...", "url":"http://mmbiz.qpic.cn/..."}
```

**没有 errcode 字段。**

我的脚本原本用 `if (errcode === 0)` 判断成功，结果把这个成功响应判成了失败，导致拿到的 media_id 根本没往下传，白白多跑了两轮。

```js
// ❌ 成功响应里没有 errcode，这个判断永远不成立
if (res.errcode === 0) { /* 拿到 media_id */ }

// ✅ 判定成功要看结果字段本身
if (res.media_id) { /* 上传成功 */ }
if (res.access_token) { /* token 成功 */ }
```

### 坑二：草稿的封面是必填，但文档的"必填"列写着"否"

这一条最坑。官方 `draft/add` 文档的参数表里，`thumb_media_id` 的**必填列标注是"否"**，但在字段说明里跟着一句：

> `article_type` 为图文消息（news）时必填，图文消息的封面图片素材 id（必须是永久 MediaID）

**必填性的真实约束写在说明里，不在必填列里。** 只看表格就会翻车。

正确做法：先调 `material/add_material?type=image` 上传封面拿 media_id，再带着它去建草稿。顺序不能反。

### 坑三：Node 的 FormData 上传微信接口会失败

上传素材是 multipart 请求。用 Node 内置的 FormData 提交，微信返回的内容解析不出 JSON。

正确做法：手工构造 multipart body——自己定义 boundary，手动拼 Content-Disposition 和 Content-Type 头，再拼二进制内容和结尾分隔符。

```js
const boundary = '----WeChatBoundary' + Date.now().toString(16);

const head =
  `--${boundary}\r\n` +
  `Content-Disposition: form-data; name="media"; filename="cover.jpg"\r\n` +
  `Content-Type: image/jpeg\r\n\r\n`;
const tail = `\r\n--${boundary}--\r\n`;

const body = Buffer.concat([
  Buffer.from(head, 'utf8'),
  fs.readFileSync('./cover.jpg'),
  Buffer.from(tail, 'utf8'),
]);

await fetch(
  `https://api.weixin.qq.com/cgi-bin/material/add_material?access_token=${token}&type=image`,
  {
    method: 'POST',
    headers: { 'Content-Type': `multipart/form-data; boundary=${boundary}` },
    body,
  }
);
```

三个容易写错的点：分隔符必须是 `\r\n` 不是 `\n`；结尾必须补 `--boundary--`；字段名必须是 `media`。

换掉之后一次就通了。

### 坑四：40164 会回显两个 IP 形式

前面说过，IPv4 和 `::ffff:` 映射形式要都留意。这个小细节能让排查时间从半小时缩到两分钟。

### 坑五：标题和摘要的长度上限，官方文档和第三方教程说的都不对

这一条是打通之后专门补测才发现的。前四个坑的文档只是没说清，这个是**文档本身写错了**。

官方 `draft/add` 文档写的是"`title` 总长度不超过 32 个字"、"`digest` 总长度不超过 128 个字"；第三方教程普遍写"标题 ≤ 64 字节、摘要 ≤ 120 字节"。

**实测下来两套都错，但错法不一样。**

真实规则是**加权长度**：中文字符计 2，ASCII 字符计 1——也就是 **GBK 字节数**。

| 字段 | 加权上限 | 等价中文字数 | 等价纯 ASCII 字符数 |
|---|---|---|---|
| `title` | 128 | 64 个字 | 128 个字符 |
| `digest` | 240 | 120 个字 | 240 个字符 |

12 个数据点交叉验证全部吻合。卡在边界上的两个例子：

- 标题 63 个中文 + 2 个字母（= 128）成功；再加一个字符（= 129）报 45003
- 纯 ASCII 标题 128 个成功，129 个报错

**两套数据分别错在哪：**

- **"64 / 120 字节"——数字对了，单位错了。** 64 是"中文字数"，不是字节数。64 个中文字实际占 128 个加权单位，差了一倍。大概率是有人用中文测出临界值 64 字，顺口说成了 64 字节。
- **官方文档的"32 字 / 128 字"——与实测均不符。** 有意思的是 128 确实出现了，但它是 `title` 的**加权上限**，跟 `digest` 的**字数**没有关系。

**排查方法（这一步才是关键）：只用一个字符类测试，分不出规则。**

64 个中文字恰好等于 192 个 UTF-8 字节。如果只用中文测，"64 个字"和"192 字节"两种规则的输出**完全一样**，你永远区分不出来。必须补一组**纯 ASCII 对照**：128 个 ASCII 字符成功、129 个失败——这才看出中文和西文的权重是 2:1。

同理，只按"能不能成功"判断，也定位不出真实数值：25 个字在两套说法下都会成功，它的失败只能排除掉"64 字节"这一种假设，不能证明"32 字"成立。

**同一页文档还有一条也没兑现。** 官方还写着 `content`"必须少于 2 万字符"。实测把一份 **54,809 字符**的正文（10 张表、286 个带样式的标签）推进草稿箱，一次通过，回读逐字一致、零截断。

**这条限制和标题长度是同一个毛病：文档写得比运行时严。** 按它自我设限，等于白丢一半额度——正文这边丢掉的额度更大。

**动作**：定标题和摘要时按加权长度累加——中文算 2、ASCII 算 1，`title` 控制在 128 以内，`digest` 控制在 240 以内。**别再按文档的"32 字"卡，那会白白浪费一半可用额度。**

## 六、AI 在这件事上判断错了三次

复盘下来，我的 AI 助手总共错了三次，而且三次性质各不相同。

| 它的判断 | 实际情况 | 错在哪 |
|---|---|---|
| IP 白名单只在公众平台后台，不用去开发者平台 | 2025-12-01 已迁移到开发者平台 | 平台规则更新，它的知识没跟上 |
| 个人主体订阅号大概率吃 48001，不乐观 | 实测三个接口全通 | 它把社区经验当成了定论 |
| 草稿的封面字段不传就行 | 封面是硬性要求 | 参数语义理解有偏差 |

这三次误判挺有代表性，对应三类系统性弱点：

**第一次是知识时效问题。** 平台规则会变，AI 的训练数据有截止日期。凡是"去哪儿找什么"这类问题，它给的路径都可能是过期的。**动作：涉及后台入口路径的判断，一律去官方文档核对。**

**第二次是信息源污染。** 社区里"个人号一律没权限"的说法流传很广，但那是特定时期的经验（发布权限被回收），不能当成平台规则。**动作：把 AI 的结论当成假设，不当成事实；有冲突就实测。**

**第三次是文档理解偏差。** 官方文档标注某个字段"非必填"，但实际运行时会校验。文档和运行时行为不一致。**动作：以报错码为准，反查文档。**

结论：**AI 能极大加速这个过程**——脚本是它写的，报错是它解读的，坑也是它逐个定位的；但凡是涉及"平台当前状态"的判断，都必须拿真实账号实测，不能采信任何二手结论，包括 AI 的。

所以最终的工作流是：

省掉的是排版、配图、上传这些纯体力活（保守估计一篇省半小时到一小时），保留下来的恰恰是该由人判断的部分：**这篇值不值得发、标题够不够抓人、观点站不站得住。**

这个分工我觉得挺合理。

## 八、对内容运营的三条启示

**1. 平台 API 的"当前状态"必须实测，官方文档也只能当线索。**

- 依据：本次三份材料两个结论，文档与运行时行为不一致（`thumb_media_id` 的必填矛盾）；文档入口在 2025 年内改过一次；`title` / `digest` 的长度上限更是**文档直接写错**，与实测差一倍。
- 动作：任何涉及权限、路径、限制的判断，先用最小成本实测一次，再决定要不要投入自动化。

**2. AI 的价值在"加速执行 + 解读报错"，不在"判断平台规则"。**

- 依据：三次误判全部落在"平台当前状态"这一类问题上；而脚本编写、报错解读、坑位定位它做得又快又准。
- 动作：把 AI 用在执行层（写脚本、解析错误、生成排版），把判断层留给自己或实测。

**3. 验证设计本身会成为新的错误来源。**

- 依据：判断长度限制时，只拿中文测临界值——"64 个字"和"192 字节"两种规则输出完全相同，测试点选得再准也分不出来；而"测试成功"被读成了"某一套假设成立"，实际上它只排除掉了另一套。
- 动作：设计验证时先问一句——**我的测试输入，能让候选规则产生不同的输出吗？** 如果不能，测试结果是无效证据。

**4. 自动化的边界应该画在"判断"之前。**

- 依据：草稿链路能全自动，发布链路不能。链路上每一个需要判断的节点，恰好也是平台限制最严的节点。
- 动作：先梳理流程里哪些是体力活、哪些是决策点，只自动化前者。

| 40013 | AppID 无效 | 检查是否复制完整 |
| 48001 | 接口无权限 | 账号类型不支持该接口 |
| 40007 | media_id 无效或缺失 | 补封面素材 |
| 45003 / 45004 | 标题 / 摘要超长（**按 GBK 加权计算**） | `title` ≤ 128 加权单位，`digest` ≤ 240 加权单位；中文计 2、ASCII 计 1。详见坑五。 |

## 附录 B：完整调用链

```
1. GET  /cgi-bin/token?grant_type=client_credential&appid=&secret=
        → access_token（有效期 7200 秒，需缓存复用）

2. POST /cgi-bin/material/add_material?access_token=&type=image
        Content-Type: multipart/form-data，字段名 media
        → 封面素材 media_id

3. POST /cgi-bin/draft/add?access_token=
        {"articles":[{"title":"...","content":"<html>","thumb_media_id":"..."}]}
        → 草稿 media_id
```

正文内嵌图片另走 `/cgi-bin/media/uploadimg`，返回 URL 而非 media_id。

两个注意点：`draft/add` 应在服务端调用，不可从前端（小程序、网页、APP）直调；草稿被群发或发布后会从草稿箱移除，**草稿箱是发布前状态，不是长期存储**，业务侧记录要自己留。

## 附录 C：微信图文排版的兼容性硬规则

推送草稿时会用到，一并记下来：

- **唯一可靠的结构是 table**：用 `<table>` + `<tr>` + `<td>` 作骨架，样式打在 `<td>` 上，内容放 `<p>` 里。思路等同 HTML 邮件。
- **可用样式**：`color`、`background-color`、`font-size`、`font-weight`、`padding`、`margin`、`border`、`text-align`、`line-height`
- **禁用样式**：`border-radius`、`position`、`linear-gradient`、伪元素 —— 微信编辑器不识别，会直接裂开
- **标题 / 摘要长度**：按 GBK 加权算（中文 2、ASCII 1），`title` ≤ 128、`digest` ≤ 240，见坑五
- **正文限制**：官方标注"必须少于 2 万字符、小于 1MB"，JS 会被移除。**实测 54,809 字符一次推入成功，字符上限未生效**（见坑五）
- **正文图片来源**：必须走「上传图文消息内的图片获取 URL」接口，外部图片 URL 会被过滤
